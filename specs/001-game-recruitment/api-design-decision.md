# API設計方針

決定日: 2026-10-03

## 決定

学習目的を兼ねて、ゲーム募集掲示板の操作をHTTP APIとして設計し、
その入力・出力・認証条件・エラーをOpenAPI形式で定義する。
実装前に各機能の `contracts/openapi.yaml` を作成し、API契約を確認する。
アカウント契約は登録・認証、掲示板契約は募集・参加を担当し、認証条件の整合を設計時に確認する。

これは設計計画への入力であり、完成した実装計画やAPI契約ではない。
業務要件の正本は [掲示板仕様](spec.md) と [アカウント仕様](../002-account/spec.md) とする。

Java側はSpring Boot、画面側はReactとTypeScriptを使用する（ユーザー指定）。
TypeScriptは `strict` を有効にする。型チェックとは別に、入力と外部データの実行時検証も設計する。
データベースはPostgreSQLを使用する（ユーザー指定）。
両機能の設計でこの技術選択を共通に使用する。

## 認証に関する確定方針

- 学習目的を兼ねて署名付きJWTを使用し、HttpOnly Cookieに保存する。
- Cookieによる認証に合わせ、CSRF対策を組み込む。
- JWTはログインごとに別の識別番号を持ち、有効期間は発行から1時間とする。自動更新・リフレッシュトークンは初版では導入しない。
- ログアウトではJWTの識別番号と期限をPostgreSQLの無効化一覧に登録し、ブラウザのCookieを削除する。
- 認証が必要な操作ではJWTの署名・期限などと無効化一覧を確認し、失効したJWTを拒否する。
- ログアウトの成功はサーバー側の無効化が成立してから返す。
- 無効化の記録はJWTの有効期限以降に削除できる。
- 複数ブラウザ・端末の同時ログインを許可し、ログアウトは提示されたJWTだけを無効化する。同じCookieを共有するタブには同じログアウトが適用される。
- 署名アルゴリズム、鍵の管理、Cookie属性の詳細、CSRF方式、無効化一覧の整理方法は設計計画で具体化する。

## 契約に含める範囲

- アカウント登録、ログイン、ログアウト。
- 固定ゲーム一覧、募集一覧のゲーム絞り込み・ページ分割、募集詳細。
- 募集作成、即時参加、参加キャンセル。
- 募集の手動締め切り、再開、中止。
- 合流情報の閲覧・編集と、状態・本人関係によるアクセス制限。
- マイページの作成募集・参加募集。

テスト用データ初期化を一般利用者向けAPIとして公開しない。

## 検証方針

- OpenAPI文書の形式と内部参照を検証する。
- 実装時は、入力・出力・エラーが契約に一致することをテストする。
- 定員超過防止、時刻境界、本人の権限、状態遷移などの業務ルールは、
  OpenAPI文書の検証とは別に、spec.mdに基づいてテストする。
- 契約変更が必要な場合は実装より先に契約を更新し、業務要件に影響する場合は
  spec.mdも先に更新する。

## ローカル開発環境

- PostgreSQLだけをDockerで動かす。
- Spring BootとReactの開発用プロセスはPC上で起動する。
- ブラウザのReactはSpring BootのAPIを呼び、Spring BootがPostgreSQLへ接続する。
- PostgreSQLの起動設定は `compose.yaml` にまとめ、データはボリュームに保存する。
- Dockerのコマンドと設定項目は学習できるよう、起動・停止・データ保持の意味を実行ガイドで説明する。
- 公開先の構成はこのローカル開発構成とは別に設計する。

## 次の設計で決めること

- Spring BootとReactのバージョン、アプリ内の構成。
- 確定した認証方針の具体化と、公開情報・合流情報の取得の分離。
- APIのURL、入力・出力、応答コード、エラー形式。
- OpenAPIのバージョンと検証方法。

OpenAPI採用だけを理由に、アプリを別サービスへ分割したり、
APIコードの自動生成を必須にしたりしない。
